## 1. 问题

现状（`src/client.css`）：

```css
.chub-channels{display:grid;grid-template-columns:repeat(auto-fill,minmax(380px,1fr));
               gap:12px;align-items:start}     /* ← start：卡片各按自身内容高 */
.chub-acctlist{display:flex;flex-direction:column;gap:7px}  /* ← 一个账号 = 一整块 */
```

- 卡片高度**由账号数量决定**：账号块是纵向列表，多一个账号就多一整块（约 200px）；
- 网格**按行对齐**（`align-items:start`），同一行里最高的那张卡决定行高，
  其余卡片下方留出等高的空白。

于是「2 个账号的渠道」旁边那张「1 个账号的渠道」下面就是一整块死白 ——
正是反馈里说的「有的两个账号、有的单账号留下很多空隙」。

### 实测数字（现状）

| 视口 | 列数 | 网格总高 | 行内空洞合计 | 行尾空格 | 卡内空白合计 |
| ---- | ---- | -------- | ------------ | -------- | ------------ |
| 1000 | 2 | 1634 | 383 | 256 | 0 |
| 1280 | 2 | 1542 | 383 | 225 | 0 |
| 1440 | 3 | 1255 | **634** | 512 | 0 |
| 1680 | 3 | 1255 | **634** | 512 | 0 |
| 1920 | 4 | 999 | **1009** | 380 | 0 |

三个指标（`artifacts/harness/measure.mjs`）：

- **行内空洞**：每一行里 `Σ(该行最高卡 − 每张卡高度)`；
- **行尾空格**：这一行实际占了几列（跨列卡按占 2 格算），剩下的空格数 × 行高。
  它和「行内空洞」不同 —— 后者是卡片之间的高度差，前者是**整格没被占**，
  只在「卡片数除不尽列数」时出现，任何方案都无法完全消除；
- **卡内空白**：每张卡内容盒底边 − 最后一个子元素底边（`align-items:stretch`
  之后空白若被搬进卡里，这个数会涨起来 —— 用它防止「洞只是换了个位置」）。

1440px 下 634px 的构成（**2026-10-21 实测**每卡高度，按屏幕上从左到右）：

- 第一行：WorkBuddy **619px**（2 个账号），Raccoon 368px、Trae 368px
  → 空洞 `(619−368) × 2 = 502px`；
- 第二行：Loomy 360px、LobsterAI 368px、Qoder 244px
  → 空洞 `8 + 124 = 132px`；
- 第三行：CodeBuddy 单独一行 244px，右侧空 2 格 → 行尾空格 `(244+12) × 2 = 512px`。

也就是说，**仅「双账号卡与单账号卡同排」这一件事就制造了 502px 的死白**。

> ⚠️ 以上是**当时那份渠道构成**下的实测快照。此后构成变过：LobsterAI 已于
> 2026-10-23 整体移除，现为 9 个渠道 / 11 个账号（buddy 2、trae 2，其余各 1），
> 第二行已不含 LobsterAI、其 `132px` 空洞数字因此**不再对应当前构成**。
> 未重新测量的数字不做外推 —— 要按当前构成更新，需重新实测各卡高度。
> 但本节的**结论不受影响**：双账号卡（619px）仍与 368px 的单账号卡同排，
> `502px` 死白依然是待解决的问题本身。

## 2. 根因与三条修法

不是间距没调好，而是「**卡片高度随账号数变化**」与「**网格要求同行卡片等高
对齐**」这两件事同时成立。只有三种出路，每种都有明确代价：

| 修法 | 洞去哪了 | 代价 |
| ---- | -------- | ---- |
| 拉平高度（`stretch`） | 搬进卡片内部 | 卡底出现空白，需要给它找去处 |
| 放弃行对齐（瀑布流） | 列内自平衡，洞消失 | 阅读顺序变成「先列后行」，列底不齐 |
| 压缩高度差本身 | 差值变小 | 可能牺牲信息密度或列数 |

方案 E 同时用「压缩高度差」（账号并排）+「拉平高度」（行内等高），于是残差
小到可以被账号框吸收，不需要任何占位块。

## 3. 候选方案与实测

所有方案都以**追加样式**的方式在真实渲染里试过（`artifacts/harness/proto-*.css`，
逐个 `node artifacts/harness/shot.mjs channels 1440 900 <css>`），`src/` 未动。

| 方案 | 做法 | 1440 列数 | 1440 网格高 | 行内空洞 | 行尾空格 | 卡内空白 | 评价 |
| ---- | ---- | --------- | ----------- | -------- | -------- | -------- | ---- |
| 现状 | — | 3 | 1255 | 634 | 512 | 0 | 问题本身 |
| **E（推荐）** | 多账号卡跨 2 列 + 账号并排 + 行内等高 | 3 | **1004** | **0** | **256** | **0** | 空洞归零，只剩「卡片数除不尽列数」的一格 |
| A | 行内等高 + 卡底「＋ 添加账号」页脚（可伸缩） | 3 | 1369 | 0 | 512 | 0 | 洞变成一大块虚线占位，页面反而更长 |
| A2 | 同 A，但页脚固定 32px | 3 | 1387 | 0 | 600 | 308 | 占位压小了，剩余空白仍留在卡底 |
| B | CSS 瀑布流（`columns`） | 3 | 1011 | 618 | 1644 | 0 | 洞没消失（只是散在列里），顺序变「先列后行」 |
| C | 账号并排，卡片最小宽仍 380px | 3 | 1219 | 598 | 512 | 0 | 3 列时每卡太窄，账号又退回上下堆叠 |
| C2 | 账号并排 + 卡片最小宽 520px | 2 | 1286 | 152 | 225 | 0 | 密度掉到 2 列 |
| C4 | 只做行内等高，余量给账号块 | 3 | 1255 | 0 | 512 | 0 † | 空洞归零，但空白堆在「模型 ↔ 操作行」之间 |
| D | 行内等高，操作行贴底 | 3 | 1255 | 0 | 512 | 0 † | 同上，空白集中在账号框内部 |
| F | 账号块压成横向密集行 | 3 | 1118 | 0 | 512 | 0 | 账号信息变挤（到期/额度/签到挤在一行） |
| G | 保序等高 + 单账号卡加「幽灵账号位」 | 3 | 1506 | 0 | 512 | 0 | 洞换成虚线占位，页面最长 |

† C4 / D 的「卡内空白」按「内容盒底边 − 最后一个子元素底边」算是 0，因为
拉伸出来的高度被账号框吸收了；但那块高度在账号框内部**仍然可见**（是「模型」
折叠条与操作按钮之间的一大段空档）。这也是为什么这几个指标要一起看：只看
其中一个，就能被「把洞挪个位置」的方案骗过去。

结论：

- **A / A2 / G 把洞换成虚线占位** —— 用户看到的仍是一块空，而且页面变长
  （A 的占位随行高伸缩，反而比原来的洞更显眼）；
- **C4 / D 把洞搬进卡片内部** —— 指标归零但视觉上仍是空白，只是换了位置；
- **B 没有真正消除洞**，还牺牲了阅读顺序；
- **C / C2 牺牲列密度**（3 列下账号又退回堆叠，或干脆掉到 2 列）；
- **F 靠压缩账号块换取高度**，可读性下降；
- **E 把「卡片高度差」这一类空洞彻底消除**，只剩「行尾空格」这一格。

关于剩下的「行尾空格」：1440px 下是 6 张单列卡 + 1 张双列卡 = 8 格铺 3 列，
必然剩 1 格；2560px 下是 8 格铺 6 列，剩 4 格。它是**列位总数除以列数的
余数**，与账号多少无关，任何网格方案都消不掉（除非允许卡片不等宽地塞进
余数格）。现状的行内空洞则**随账号数线性增长**：多一个账号，同排的单账号卡
就多空一整块。这个差别才是方案 E 的价值。

各视口下方案 E 的完整数据：

| 视口 | 列数 | 网格总高 | 行内空洞 | 行尾空格 | 卡内空白 |
| ---- | ---- | -------- | -------- | -------- | -------- |
| 1000 | 2 | 1384 | 0 | 0 | 0 |
| 1280 | 2 | 1345 | 0 | 0 | 0 |
| 1440 | 3 | 1004 | 0 | 256 | 0 |
| 1680 | 3 | 1004 | 0 | 256 | 0 |
| 1920 | 4 | 748 | 0 | 0 | 0 |
| 2200 | 5 | 748 | 0 | 760 | 0 |
| 2560 | 6 | 625 | 0 | 1024 | 0 |

> **行内空洞在所有宽度下都是 0**，这是方案 E 的硬指标。
> `行尾空格` 只取决于「8 个列位铺几列」：1000 / 1280（2 列）与 1920（4 列）
> 恰好排满，1440 / 1680（3 列）剩 1 格，2200（5 列）剩 2 格，2560（6 列）剩 4 格。
> 它**只与格子数有关，与账号多少无关**；现状的空洞则随账号数线性增长
> （每多一个账号，同排单账号卡就多空一整块）。

## 4. 推荐方案 E

### 4.1 布局规则

```css
/* 1. 行内等高：同一行卡片拉平；残差交给卡内的可伸缩子项 */
.chub-channels{grid-template-columns:repeat(auto-fill,minmax(380px,1fr));align-items:stretch}
.chub-channel{height:100%}

/* 2. 账号列表吃掉卡片剩余高度（单账号卡也适用） */
.chub-acctlist{flex:1 1 auto;min-height:0}

/* 3. 2 个以上账号的卡片跨两列 —— 高度差被宽度吸收 */
.chub-channel[data-multi]{grid-column:span 2}

/* 4. 跨列卡里账号并排；auto-fit 让 3～4 个账号也能排满一行 */
.chub-channel[data-multi]>.chub-acctlist{
  display:grid;grid-template-columns:repeat(auto-fit,minmax(210px,1fr));
  grid-auto-rows:1fr;gap:7px;
}

/* 5. 操作行贴底：被拉伸出来的几像素落在账号框内部，而不是卡底 */
.chub-acct>.chub-acctacts{margin-top:auto}

/* 6. 未接入（0 账号）的空状态占满剩余高度并居中，避免「小虚线框 + 一大片白」 */
.chub-channel>.chub-empty{flex:1 1 auto;justify-content:center}

/* 7. ⚠️ 窄容器必须收回跨列：单列网格里 `span 2` 会造出隐式第二列，
      卡片被挤成半宽（本方案唯一的硬性约束，实测 780px 会复现） */
@container chub (max-width:820px){
  .chub-channel[data-multi]{grid-column:auto}
}
```

### 4.2 组件侧改动（`src/client.ts`，一处）

```ts
h("article", {
  key: c.id,
  className: "chub-channel",
  "data-state": state,
  "data-multi": accounts.length > 1 ? "" : undefined,   // ← 唯一新增
  style: { "--chan-accent": accentOf(c.id) } as any,
}, …)
```

**为什么用显式属性而不是 `:has(.chub-acct + .chub-acct)`**：后者今天也能命中
（账号块是 `.chub-acctlist` 的直接子元素，中间没有别的兄弟），但它把**布局
分支绑在标记结构上**：以后若给账号块包一层滚动容器、或在两个账号之间插入
分隔线/「已停用」分组标题，`+` 就失效，卡片会**静默**退回单列 —— 不报错、
不警告，只是布局变了。显式 `data-multi` 是稳定契约，也便于测试断言。

若不想动组件，`:has()` 版本可作为过渡（已验证在 Chromium 下工作），但落地
时应在 `tests/client.test.mjs` 里加一条「双账号渠道的卡片确实跨列」的断言，
把这个隐式依赖钉住。

### 4.3 为什么不用 `grid-auto-flow:dense`

`dense` 能让后面的小卡回填跨列卡留下的空位，行内空洞同样是 0；但它会让
**视觉顺序与 DOM 顺序不一致**。实测（把双账号渠道排到第 3 位）时，`dense`
会把第 4 张单账号卡提到第一行，用户看到的顺序变成
「Raccoon、Trae、Loomy、WorkBuddy…」，与直觉冲突。

**第二轮修正（2026-10-22，用户带截图报障）**：最初的跨列方案有一个我没预料到
的结构性缺陷 —— 跨列卡**放不进行尾剩下的那一格**时会整体换行，于是前一行
右侧空出一整格。用户的真实顺序恰好命中：华为码道（1 个账号）在第 1 行，
紧接着的 CodeBuddy（2 个账号）放不进去被顶到第 2 行，形成 `1-2-1`。

只用 CSS 修不掉它（`dense` 会让视觉顺序偏离 DOM 顺序，`order` 同理）。
**正确做法是在组件里按实际列数把卡片装成满行**，且真的重排 DOM：

```ts
// 跨列卡后面紧跟足够的单列卡把这一行填满
const perWide = Math.max(0, columns - 2);   // 2 列 → 0，3 列 → 1，4 列 → 2
```

`columns` 由 `ResizeObserver` 实测 `grid-template-columns` 的轨道数得到
（不能用视口宽度猜：侧栏和页边距会吃掉宽度）。实测效果：

| 场景（`?multi=1`，两张跨列卡） | 修前 gaps | 修后 gaps |
| --- | --- | --- |
| 1000 / 1280（2 列，用户截图那种） | 381 / 381 | **0 / 0** |
| 1440（3 列） | 893 | **0** |
| 1680（3 列） | 893 | **0** |
| 网格总高（1440） | 1384 | **1120** |

修后的排布规律：**3 列时每行 = 跨列卡占 2 格 + 1 张单列卡补齐；2 列时每张
跨列卡独占一行**（`perWide = columns - 2`，2 列时为 0）。

### 4.4 账号数 ≥ 3 与窄窗口

`auto-fit` 让账号块随可用宽度自动决定列数：3 个账号在 640px 宽的跨列卡里
排成 3 列（每个约 200px），不会退化成「2 + 1」两行；`grid-auto-rows:1fr`
保证同一行的账号框等高，操作按钮底边对齐。

780px 时 `.chub-channels` 已是单列（既有规则 `@container chub (max-width:820px)`），
跨列被收回，卡片恢复整行宽，账号在卡内并排。

## 5. 验收标准

1. `measure.mjs` 在 1000 / 1280 / 1440 / 1680 / 1920 五档下 `holes = 0`、`dead = 0`，
   且 `gaps` 不超过一个列位（1440 下即 256px）；
2. 780px 视口下卡片**整行宽**（跨列已收回），不是半宽；
3. 3 个账号的渠道（`?tri=1`）里账号排成 3 列、操作行底边对齐；
4. 0 账号渠道的「尚未添加账号」垂直居中，卡内无残留空白；
5. 既有规则不受影响：`:hover` 抬升、`data-state` 顶部色条、`@container` 窄屏 padding；
6. 新增一条 `tests/client.test.mjs` 断言：产物里存在 `data-multi`，且 CSS 含
   `@container chub (max-width:820px)` 下的 `grid-column:auto` 兜底
   （否则窄屏半宽问题会回归）。

## 6. 复现方式

渲染夹具在 `artifacts/harness/`（该目录在 `.gitignore` 里，属于一次性诊断
工具，不入库）。它加载**真实的 `dist/client.js`**，用模拟 RPC 数据渲染，
通过 CDP 直接驱动 headless Chrome，不依赖 Playwright。

```powershell
npm run build     # 夹具读 dist/client.js，改过 src 后先构建

# 真实 Chromium 截图（2x 设备像素）。落地后**不需要**再传原型 CSS。
node artifacts/harness/shot.mjs channels 1440 900

# 量化对比：列数 / 网格高 / 行内空洞 / 行尾空格 / 卡内空白
node artifacts/harness/measure.mjs

# 逐卡空白明细（哪张卡、多高、底部空多少、账号列表内部还空多少）
node artifacts/harness/deadspace.mjs "" 1280

# 其他数据形态（QUERY 由脚本归一化，`?tri=1` / `tri=1` 都行）
$env:QUERY="?tri=1"        # 给 WorkBuddy 加第三个账号
$env:QUERY="?multi=1"      # 再给 Raccoon 加一个账号（两个双账号渠道）
$env:QUERY="?real=1"       # 用户真实顺序：华为码道(1) → CodeBuddy(2) → 其余(1)
```

> 截图文件名会带上形态标签（如 `shot-channels-1440-tri-1.png`），否则同一份
> 构建的「3 个账号」图会覆盖默认形态的图。

需要看**改动前**的样子时：临时 `git stash` 掉 `src/client.ts` 与
`src/client.css` 的改动 → `npm run build` → 截图 → 还原改动 → 再 `npm run build`。

> 截图与对比图都留在 `artifacts/harness/`（已被 `.gitignore` 排除），
> **不导出到 `docs/`**，也不入库 —— 它们是一次性诊断产物，结论以本文的
> 实测数字为准。

> 夹具用 `document.body.dataset.ready` 与脚本通信；`shot.mjs` / `measure.mjs`
> 在注入原型样式前，会按「账号数 > 1」补上 `data-multi` 属性。
> **方案 E 已落地后，组件自己就会输出这个属性**，夹具那一步只是幂等的兜底，
> 不会改变测量结果（第 8 节的数字是直接跑 `measure.mjs` 不带任何 CSS 得到的）。

复核过，且**每种形态下 `holes` 恒为 0**：

| 形态 | 含义 | 1440 的 gaps | 说明 |
| ---- | ---- | ------------ | ---- |

网格布局都消不掉的固有代价。
